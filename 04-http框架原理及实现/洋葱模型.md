# 中间件洋葱模型

HTTP 框架里的**洋葱模型**（onion model）描述的是：多个中间件如何一层层包住业务 handler，让请求从外往里进、响应从里往外回。

本目录 `minihttp` 的实现见 `minihttp/app.py` 的 `handle`。

## 核心概念

| 概念 | 含义 | 典型例子 |
|---|---|---|
| 中间件（middleware） | 夹在「收到请求」和「业务 handler」之间的可插拔逻辑 | 日志、鉴权、计时、CORS |
| `call_next` | 「继续往内层走」的函数；调用它才会进入下一层 / handler | `response = call_next(request)` |
| 洋葱 | 每一层都能在 `call_next` **之前**处理请求、**之后**处理响应 | 进：A→B→handler；出：handler→B→A |
| 注册顺序 | 先注册的在最外层：先看到请求，最后看到响应 | `[access_log, auth]` → log 最外 |

关系可以记成：

```
请求 ──► [中间件 A] ──► [中间件 B] ──► handler
响应 ◄── [中间件 A] ◄── [中间件 B] ◄──
```

像剥洋葱：外层先进先出（对响应而言是后处理）。

## 为什么需要洋葱模型

没有统一中间件时，鉴权、日志、计时只能塞进每个 handler，或写一堆全局钩子，难复用也难组合。

洋葱模型把横切逻辑抽成「包一层」：

1. **横切复用**：日志 / 鉴权写一次，所有路由自动经过。
2. **前后都能插手**：`call_next` 前改请求，后改响应（加 header、记耗时）。
3. **可短路**：鉴权失败可以直接 `return Response(...)`，不调用 `call_next`，内层根本不跑。
4. **顺序可控**：注册顺序 = 外包顺序，组合方式直观。

## 中间件长什么样

约定签名（与 `MiniHTTP` 一致）：

```python
def middleware(request, call_next) -> Response:
    # 1. call_next 之前：看 / 改请求，或直接返回（短路）
    response = call_next(request)   # 2. 进入内层
    # 3. call_next 之后：看 / 改响应
    return response
```

`example.py` 里的访问日志：

```python
@app.middleware
def access_log(request, call_next):
    response = call_next(request)          # 先放行到内层
    client = request.client_addr[0] if request.client_addr else "-"
    print(f"{client} {request.method} {request.path} -> {response.status}")
    return response
```

注意：日志在 `call_next` **之后**打印，才能拿到真实 `status`。

## 执行顺序：图解

假设注册了两个中间件，顺序为 `[A, B]`，最内层是路由分发 `dispatch`：

```
请求进入
   │
   ▼
┌──────────── A（最外）────────────┐
│  A 前置代码                        │
│     │                              │
│     ▼                              │
│  ┌────── B ──────┐                 │
│  │  B 前置代码     │                 │
│  │     │           │                 │
│  │     ▼           │                 │
│  │  dispatch       │  ← 匹配路由、调 handler
│  │     │           │                 │
│  │     ▼           │                 │
│  │  B 后置代码     │                 │
│  └──────┬──────────┘                 │
│         ▼                            │
│  A 后置代码                          │
└────────────┬─────────────────────────┘
             ▼
          返回响应
```

口头记：**先注册的最外层；请求先进外层，响应最后经外层。**

### 短路

若 A 在前置阶段直接返回，B 和 handler 都不会执行：

```python
@app.middleware
def require_token(request, call_next):
    if request.headers.get("Authorization") != "Bearer secret":
        return json_response({"error": "unauthorized"}, status=401)
    return call_next(request)
```

## MiniHTTP 怎么实现

关键代码在 `MiniHTTP.handle`：

```python
def handle(self, request: Request) -> Response:
    def dispatch(req: Request) -> Response:
        return self._dispatch(req)

    # 从内到外包装：list 反着遍历
    call_next = dispatch
    for mw in reversed(self.middlewares):
        next_fn = call_next

        def make_wrapper(middleware, nxt):
            def wrapper(req):
                return middleware(req, nxt)
            return wrapper

        call_next = make_wrapper(mw, next_fn)

    return call_next(request)
```

要点：

1. **内核是 `dispatch`**：路由匹配 + 调 handler + `_normalize`。
2. **`reversed` 从内往外包**：注册 `[A, B]` 时先包 B 再包 A，最终最外层是 A。
3. **`make_wrapper` 闭包工厂**：避免 `for` 循环里闭包抓到「最后一次」的 `mw` / `next_fn`（经典 Python 坑）。

等价理解（伪代码）：

```python
# 注册顺序 [A, B]
# 最终 roughly：
#   A(request, lambda r: B(r, dispatch))
```

### 注册

```python
def middleware(self, func):
    self.middlewares.append(func)
    return func
```

`@app.middleware` 不需要路径参数，所以是**直接装饰器**（对比 `@app.get("/")` 的装饰器工厂，见 README）。

## 常见写法对照

| 场景 | 写在哪 | 说明 |
|---|---|---|
| 访问日志 | `call_next` 之后 | 需要 `response.status` |
| 鉴权 / 限流 | `call_next` 之前 | 失败则短路，不进 handler |
| 计时 | 前后各记一次 | `t0` → `call_next` → 算耗时写 header |
| CORS | 之后给响应加头；OPTIONS 可短路 | 浏览器预检常直接返回 |
| 统一异常 | 包住 `call_next` 的 try/except | 本框架在 `handle` 最外层已兜底 500 |

计时示例：

```python
import time

@app.middleware
def timing(request, call_next):
    t0 = time.perf_counter()
    response = call_next(request)
    ms = (time.perf_counter() - t0) * 1000
    response.set_header("X-Process-Time", f"{ms:.1f}ms")
    return response
```

多层时注意顺序：若希望「计时包含鉴权失败的短路路径」，计时应注册在鉴权**外面**（先注册 timing）。

## 和「钩子」的差别

有的框架拆成 `before_request` / `after_request`。洋葱模型用一个函数 + `call_next` 把前后绑在一起：

- 局部变量能跨过内层（计时的 `t0` 天然可用）
- 短路语义清晰（不调 `call_next`）
- 多层嵌套时，进出顺序由包装自动保证

`before`/`after` 拆开也能做，但计时、事务（begin/commit）这类「成对逻辑」用洋葱更自然。

## 和本目录其它模块的关系

```
server.accept → Request.from_raw → app.handle（洋葱）→ Response.to_bytes
                                      │
                                      └─ 最内层 _dispatch：router + handler + _normalize
```

- **server**：只管字节进出，不知道中间件。
- **router / handler**：只关心业务，不知道外面包了几层。
- **洋葱**：把横切关注点夹在两者之间，这就是「框架」比裸 `socket` 多出来的那一层抽象。

## 小结

1. 中间件 = `f(request, call_next) -> Response`。
2. 请求外→内，响应内→外，形似洋葱。
3. MiniHTTP 用 `reversed` + 闭包从内往外包装；先注册的最外层。
4. 不调用 `call_next` = 短路，内层不执行。
